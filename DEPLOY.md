# Continuous Railway deployment

Prepared, not deployed. Select Kronos1095/DuoStockChecker as the Railway service source, repository root. Dockerfile and railway.toml are included. Use ONE replica. Attach a persistent volume at /data before deploying (stores alert history and SQLite outbox). Keep Serverless/App Sleeping OFF. Generate a Railway domain to view the live dashboard and /health. GitHub Pages is the slower fallback dashboard; it does not show the worker's 30-second results.

Variables: NTFY_TOPIC (required for alerts); optional NTFY_TOKEN for an authorized ntfy.sh topic. Keep credentials in Railway variables, never in git. APPLE_HOT_ZIP=10001, APPLE_POLL_SECONDS=30, ATT_POLL_SECONDS=120, STOCK_DATA_DIR=/data. Optional BESTBUY_API_KEY. SEND_TEST_ON_START=true sends a labeled test on worker startup. The service starts without a topic but shows notificationsConfigured=false at /health: that is not notification readiness.

Install the native ntfy app on each device where alerts are wanted and subscribe to the EXACT topic on https://ntfy.sh. Allow notifications and sounds; exclude ntfy from Scheduled Summary and allow it in any active Focus. Lock the device and verify the startup test arrives promptly. A successful HTTP publish is only server acceptance, not proof of device delivery. Test each device separately, then observe a real or controlled availability transition. iOS/Apple push infrastructure and internet connectivity can delay delivery; zero-latency delivery is not guaranteed. Public random topics are not access-controlled. Do not configure the same topic in GitHub Actions while worker alerts are active, or independent systems may duplicate alerts.

Apple nearest-store polling starts every ~30 seconds if requests finish within that interval, backs off to 300 seconds after errors, and never overlaps in its lane. AT&T has a separate 120-second lane. Wide Apple scans run every 300 seconds and do not change hot-lane alert state. Only nearby Apple stores receive 30-second checks; other stores are covered by the regional fallback. The persistent outbox queues a newly available store (including the first scan), retries at most four times, and expires unsent alerts after 120 seconds. Availability may disappear before delivery. A crash after delivery but before recording success can cause one duplicate. One replica and a persistent volume are mandatory for deduplication. The fast lane runs independently of regional scans, but provider throttling may still affect both.

Health: /health reports lane heartbeat responsiveness, not inventory correctness. /notification-health.json reports push-server acceptance only. Review error states on the dashboard and health endpoint. Railway deployment health checks are not a substitute for external uptime monitoring. Hosting incurs Railway charges; configure spending limits in your account. Startup testing and cloud endpoint access still require live verification after deployment.
